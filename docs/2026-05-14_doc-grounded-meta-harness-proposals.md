# Documentation-grounded meta-harness — methodological proposals

## 1. Where this fits

Paper 1 (NeurIPS submission) is the **manual SimAdapter recipe** for one
elaborate tool (GEOS). It does not auto-evolve the harness. Paper 2 is
the natural follow-up: **automatically discover the adapter** given the
tool's documentation. See `docs/2026-05-02_neurips-paper-plan.md` §11
("two-paper arc — what's deferred to Paper 2") for the scope boundary.

The user-stated novelty hook is:

> An agent harness that reads/uses organized knowledge (manual,
> documentation, papers) via a meta-harness procedure that also reads
> from this knowledge. Both layers ground in the same docs; the meta
> reads docs to build a harness that reads the docs usefully.

This doc inventories what the four closest baselines actually do with
documentation, identifies the gap, then proposes concrete
methodological novelties that would land cleanly inside that gap.

## 2. Baselines — what they do with documentation

| System | Doc role | Doc structure exploited? | Outer proposer |
|---|---|---|---|
| **Meta-Harness** (Lee et al. 2026) | "Offline experience" optionally loaded into FS as another directory; proposer can grep/cat it | No — flat | Coding agent (Claude Code, Opus 4.6) with full FS access |
| **MCE** (Ye et al. 2026) | Not a first-class lever; skills *can* contain retrieval logic over arbitrary files | No — generic file/code substrate | MiniMax M2.1 meta-agent doing "agentic crossover" over skills |
| **AHE** (Lin et al. 2026) | Not modeled; harness components are prompts/tools/middleware/memory; trajectories are the signal | No — observability is over traces, not docs | GPT-5.4-high evolve-agent over NexAU file substrate |
| **SkillFoundry** (Shen et al. 2026) | "Authoritative artifacts" *priority* for skill mining; docs sit alongside repos / notebooks / papers / APIs | Partial — domain tree organizes *capabilities*, not doc sections | Staged GPT-5.4 pipeline with JSON-schema responses; high-reasoning concentrated at *resource_search* stage |
| **MoSciBench** (Liu et al. 2026) | Eval finding: naïve "add domain knowledge" actually *hurts* (48.4 → 44.9); workflow scaffolding helps (48.4 → 54.1) | n/a (benchmark paper) | n/a |

**Two important observations:**

1. None of the four systems treats documentation as a *structured
   substrate the meta-harness reasons over*. The closest is
   SkillFoundry's domain-knowledge tree, but that tree is over
   capabilities, with docs as one input source.
2. MoSciBench's negative result on naïve knowledge injection is a
   warning shot. Just stuffing the manual into the harness's context
   degrades performance. Structure has to do real work.

This is the white-space we sit in.

## 3. Problem statement (Paper 2 framing, draft)

> **Given** an elaborate scientific tool (e.g., GEOS, FEniCS, MOOSE) and
> its authoritative documentation, **automatically discover an agent
> harness** that operates the tool with measurable fidelity to its
> documented behavior, **using a meta-harness procedure that
> co-evolves** (a) the harness's runtime use of the documentation and
> (b) a structured representation of the documentation itself.

Concretely we want the meta-harness to do better than:

- **MH-baseline**: free-form coding agent with the manual dumped into
  one directory of the candidate-history FS.
- **SF-baseline**: skill mining from docs as just-another-artifact,
  with capability-axis tree.
- **AHE-baseline**: trajectory-distilled observability, no doc
  grounding.

…on the same evaluation surface (input-file authoring fidelity,
end-to-end task success, transfer to unseen tool sub-areas).

## 4. Proposed methodological novelties

We are not proposing all of these — this is a menu. Each item lists
what it claims, why existing work doesn't already do it, and how to
falsify it.

### N1. Typed document index as a first-class harness component

**Claim.** Manuals have stable *typed* structure: schema/reference vs
example/tutorial vs concept/background vs deprecation/warning sections.
The meta-harness should expose this typing to the harness via a
**typed multi-index** (one retrieval surface per type), and should
*itself* see the index as an editable component.

**Why novel.** MH treats docs as flat text. SF prioritizes
authoritative artifacts but doesn't carry their structural typing
through to the runtime retrieval surface. MCE/AHE don't model docs at
all.

**How to falsify.** Ablate: (a) single flat index; (b) typed multi-index;
(c) typed multi-index + meta-harness can edit the indices. Predict
strict ordering c > b > a, with the c→b gap quantifying value of
meta-level editing.

**Risk.** If the tool's documentation isn't actually structurally
typed (some manuals are messy prose), this collapses to a single-index
baseline. Real-world manuals (GEOS, FEniCS) are typed; this is
empirically checkable up-front.

### N2. Bipartite component–section graph

**Claim.** Maintain an explicit, editable bipartite graph between
**harness components** (skills, prompts, retrieval functions,
middleware) and **doc sections they cite or serve**. Both sides are
editable by the meta-harness; both sides have coverage state.

**Why novel.** AHE's three observability pillars are (component,
experience, decision). This is a fourth pillar — *grounding* — that AHE
explicitly does not model. SkillFoundry's tree is single-sided (it's
*capability* coverage, not component↔section).

**Concrete payoff.**
- Detect *dead sections* (never cited by any component) → either prune
  or build coverage.
- Detect *ungrounded components* (no section citation) → flag for
  documentation-justification or removal.
- Edits stay *bipartite-consistent*: every code change has to declare
  which sections it depends on or invalidates.

**How to falsify.** Compare meta-harness variants with/without the
graph on (a) regression rate per iteration, (b) generalization to held-
out tool sub-areas. If the graph doesn't reduce regressions or improve
transfer, it isn't earning its complexity.

### N3. Doc-anchored failure attribution

**Claim.** AHE's evolve-agent predicts fixes (precision 33.7%, recall
51.4%) but predicts **regressions** near-randomly (precision 11.8%,
recall 11.1%). Constrain attribution to point at one of:

  (a) a section the harness should have consulted but didn't,
  (b) a section it consulted but misinterpreted,
  (c) a section that doesn't exist in the docs (genuine gap).

**Why novel.** This converts open-ended causal reasoning into a
3-way doc-grounded classification problem with verifiable evidence.
None of MH/MCE/AHE/SF do this — their attribution surfaces are code
diffs, score deltas, or LLM-as-judge text.

**How to falsify.** Re-run AHE's regression-prediction analysis with
the constrained attribution. Hypothesis: regression-prediction
precision improves substantially (target: >25%) because the search
space is bounded and grounded. If it doesn't, the constraint doesn't
buy us anything beyond AHE's free-form reasoning.

### N4. Doc-bootstrapped seed harness

**Claim.** Replace SkillFoundry's manually-curated initial taxonomy
with a meta-harness pre-pass that *constructs* the seed harness and
typed indices by skimming the documentation: extract (entrypoints,
primary objects, top-level workflows, schema entities, deprecation
warnings) from the doc's structural metadata.

**Why novel.** SF: seed is human-curated. MH: seed is hand-engineered
starter harness. We replace the human-curation step with a doc-derived
one and treat the seed itself as part of the search trajectory the
meta-harness can revise.

**How to falsify.** Measure performance of (a) hand-curated seed, (b)
doc-bootstrapped seed, (c) doc-bootstrapped seed + meta-harness
revision. If (b) ≥ (a), automation hasn't hurt; if (c) > (b)
significantly, the meta-harness is doing useful work beyond
bootstrap.

### N5. Doc-as-soft-oracle for tests

**Claim.** Manuals contain prescriptive workflows ("the correct way
to construct an input file is…") and prohibitive constraints ("do not
nest X inside Y", "deprecated in v3.4"). Extract these as test
oracles:

- **Adherence tests**: does the harness's output match the documented
  workflow shape for a given task class?
- **Constraint tests**: does the harness ever generate output that
  violates a documented prohibition?

This is a fourth validation layer beyond SkillFoundry's exec / system /
synthetic trio.

**Why novel.** SF's synthetic tests check contract completeness and
behavioral stability — not adherence to documented best practice.
None of MH/MCE/AHE have this. Crucially, this is a test surface
available *even when downstream ground truth isn't*, which matters for
elaborate scientific tools where you can't easily run a real
simulation per iteration.

**How to falsify.** Test whether adherence/constraint passing
correlates with downstream task success. If correlation is high,
adherence tests are a cheap proxy for expensive ground-truth tests
(a real efficiency win). If low, the docs say one thing and the tool
behaves another way — interesting in itself but undermines the
proxy.

### N6. Doc-utility–weighted search budget

**Claim.** At each meta-harness iteration, allocate proposer budget
across doc sections in proportion to *empirical past utility* (which
sections were cited by harnesses that improved the score) and *coverage
deficit* (which sections have weak verified citation).

This is the SkillFoundry tree-prioritization heuristic translated from
the *capability axis* to the *doc-section axis*.

**Why novel.** MH's free-form proposer has no explicit budget
allocation — it reads what it reads. SF's allocation is over
capabilities, not doc sections. This proposal directly uses the
manual's structure as the search prior.

**How to falsify.** Compare convergence speed to a fixed quality
threshold under (a) uniform doc-budget, (b) recency-weighted budget,
(c) utility+deficit weighted. If (c) doesn't speed up convergence, the
weighting is uninformative.

### N7. Symmetric doc-consultation traces

**Claim.** Both the meta-harness proposer **and** the harness it
builds operate over the same documentation. Record both layers'
**doc-consultation traces** (which sections, which queries, which were
useful) and make them visible to the meta-harness on the next
iteration.

This gives the meta-harness a powerful self-consistency check: "would
*I* have consulted the same sections as the harness I just proposed?"

**Why novel.** MH records *execution* traces. AHE records distilled
*trajectory* evidence. Neither separates doc-consultation as a
distinguishable channel; we propose it as a first-class trace type
with its own structure.

**How to falsify.** Ablate consultation-trace visibility — give the
meta-harness only score+code, only score+code+exec-trace (MH-style),
or also doc-consultation trace. Does the third condition reduce
iteration count or improve final quality?

### N8. Negative doc-knowledge as constraints

**Claim.** Mine the manual for prohibitions, warnings, deprecations,
and pre-conditions, and compile them into **runtime guards** the
harness must respect. Violations are loud failures the meta-harness
sees.

**Why novel.** SF's contract format has "execution assumptions" but
doesn't separate positive ("how to use X") from negative ("don't use
X with Y, ever"). MH/MCE/AHE don't extract constraints at all.

**How to falsify.** Compare violation rate with/without the constraint
layer. Compare downstream task success — if constraints fire often
but task success is flat, the constraints are over-strict noise.

### N9. Doc-diff as longitudinal maintenance signal

**Claim.** Tool documentation gets updated. When a new doc version
lands, diff against the previous version and identify which harness
components depend on changed sections. This is a maintenance signal
the meta-harness uses to revise affected components.

**Why novel.** Nobody else does this. It's the longitudinal angle —
none of the four baselines run for long enough or against a moving
target to need it.

**How to falsify.** Probably not worth running in Paper 2 — this is a
long-horizon claim. Could be a "limitation acknowledged, future work"
note unless we find a real-world tool that updated mid-experiment.

## 5. Recommended Paper-2 core

If we have to pick a small number to commit to, the strongest cluster
is:

- **N1** (typed index) — earns the doc-structure framing, lowest
  implementation risk.
- **N2** (bipartite graph) — earns the meta/harness *symmetry* the
  user emphasized.
- **N3** (doc-anchored attribution) — directly attacks AHE's weakest
  link (regression prediction).
- **N5** (doc-as-soft-oracle) — gives us a test surface that works
  even when downstream ground truth is expensive.

The natural ablation lattice across these four is small (2^4 = 16,
but with prerequisites probably 6–8 meaningful conditions), and they
collectively answer one question:

> Does explicit doc-structure (typing + bipartite grounding + anchored
> attribution + adherence tests) beat both the unstructured (MH)
> upper-bound proposer and the capability-tree (SF) middle-ground?

N4 (doc-bootstrapped seed) and N6 (utility-weighted budget) are good
secondary studies. N7 (symmetric traces) is the most ambitious
self-consistency claim and probably needs its own focused study. N8
(negative knowledge) and N9 (doc-diff) are saveable for a future
paper or limitations section.

## 6. Evaluation shape (sketch)

Borrowing scDRS-style transfer evaluation from SkillFoundry:

- **In-tool evaluation**: build a doc-grounded harness for tool T₁
  (GEOS). Compare against MH-baseline, SF-baseline, AHE-baseline, and
  the manual SIA recipe from Paper 1. Metrics: input-file fidelity,
  end-to-end task success, blinded expert review of generated
  artifacts.
- **Cross-tool transfer**: take the same meta-harness procedure and
  point it at tool T₂ (FEniCS or MOOSE). Does the same procedure
  produce a working harness without re-engineering? This is the
  generalization claim Paper 2 needs.
- **Documentation-only ablation**: vary what fraction of the manual
  the meta-harness can see. If performance degrades smoothly, the
  doc grounding is doing real work. If it's flat (system works
  without the manual), we don't have a doc-grounding story at all.

## 7. Open questions

- Coding-agent vs staged-pipeline proposer (MH end of spectrum vs SF
  end). Our doc-grounding can be hosted in either, but the novelty
  case is sharper if we commit to one. Recommended: staged, because
  the per-stage JSON schemas give us natural places to plug in N1
  (per-type retrieval), N2 (graph maintenance), N3 (attribution
  classification). Coding-agent style makes those much harder to
  enforce.
- How much should the manual itself be considered editable by the
  meta-harness? SF's tree is editable; MH's offline directory is
  read-only by convention. Allowing the meta-harness to *write
  derived summaries* over doc sections (without rewriting source)
  is probably the right compromise.
- Relationship to skill-foundry's "design-skill" mode. SF's
  task-specific skill synthesis is closest to our problem but is
  per-task; we want per-tool. Is per-tool just "per-task with
  amortized skills across tasks," or genuinely different?
