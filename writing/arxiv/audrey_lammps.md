# LAMMPS Transfer Study — Paper Sections

## Main Text

**Cross-simulator transfer: LAMMPS**

We ported {R, S, X, M} to LAMMPS molecular-dynamics input-script authoring on a 9-task benchmark spanning diverse MD physics (single seed, LLM-judge metric [0–10], App. H). We ran 12 configurations across two backbone models—Claude Sonnet 4.6 and DeepSeek—to probe transfer both across simulator and across model family. The qualitative lesson transfers with a shifted factor profile. The best DeepSeek cell ({M,R,S,X}) reaches mean 7.78, versus 4.56 for vanilla DeepSeek—a 3.2-point gain. The best Claude cell ({M,R}) reaches 6.89 versus 6.33 for vanilla Claude; gains are modest because Claude already assigns mostly correct values to the required parameters even without guidance—its vanilla LLM judge score of 6.33 shows the baseline is already high. Across all 12 cells, structural scores are near-ceiling (≥ 0.976); this check primarily verifies that required commands and parameter fields are present and structurally plausible, rather than fully evaluating whether the assigned values match the ground-truth solution, which is why both models score high regardless of configuration. The LLM judge—which evaluates whether the values assigned to those parameters are correct relative to ground truth—is where Claude and DeepSeek differ. A factor-style readout on DeepSeek assigns the largest descriptive effect to M (+2.13), followed by R (+1.55), with S and X positive but smaller; on Claude, all effects are within ±0.5. This contrasts with GEOS and OpenFOAM, where forced end-of-turn verification (S) was the dominant reliability intervention. The LAMMPS result suggests the dominant transfer mechanism is informational—correct unit conventions, ensemble syntax, and task-specific command patterns—rather than workflow enforcement. Structural scores are near ceiling across all configurations, indicating that agents generally produce complete scripts and that most remaining errors involve assigning incorrect values rather than omitting required components.

## Appendix H — LAMMPS Transfer Study

**Motivation.** The main paper studies SIGA on GEOS, whose interface is a structured XML deck with explicit XSD validation. The OpenFOAM transfer study (App. G) showed the recipe extends to a schema-free, text-file simulator. To probe whether the recipe also transfers across model family and into a physically richer simulator domain, we ran a LAMMPS molecular-dynamics input-script authoring study with two backbone models across 12 factor configurations. LAMMPS differs from GEOS and OpenFOAM in several ways: its input is a sequential command script with strict ordering rules and no formal schema; a large curated example library ships with the source code; and the physics space is broader (thermostats, barostats, 2D simulations, NEMD, electrostatics, mechanical deformation). We treat the result as transfer evidence rather than a second benchmark.

**LAMMPS adaptation of R/S/X/M.** We ported the same four binary factors to LAMMPS input authoring. R replaced the GEOS RAG collections with three ChromaDB collections over LAMMPS example scripts, documentation RST files, and command syntax extracted from the LAMMPS source tree. M replaced the GEOS XML cheatsheet with a LAMMPS-specific primer covering required command ordering, unit conventions, and ten task-specific critical pitfalls (e.g., LJ lattice density semantics, region-before-create\_box ordering, unfix before switching integrators, SLLOD Couette pattern, MSD compute syntax). S replaced the GEOS XML stop hook with a LAMMPS structural stop hook that blocks turn completion if the generated script fails heuristic structural checks. X replaced xmllint with an agent-callable LAMMPS script validator applying the same structural checks as the hook. Because LAMMPS has no canonical schema for these tasks, the validator checks command presence, correct units and atom\_style, ensemble type, task-specific physics commands (fix indent, fix deform, compute msd, fix nvt/sllod, fix npt), temperature ranges, and minimum run lengths.

**Benchmark and metric.** The LAMMPS benchmark contains 9 tasks spanning a range of MD physics: Lennard-Jones melt from FCC lattice (lj\_melt, lj\_melt\_minimal), LJ FCC solid NVT equilibration (lj\_solid), 2D crack propagation (crack\_2d), 2D nanoindentation with a descending spherical indenter (lj\_indent), Couette flow via the SLLOD algorithm (couette\_flow), mean-square-displacement diffusion characterization (msd\_diffusion), TIP3P water NVT with long-range electrostatics (nvt\_water), and uniaxial tension with lateral NPT relaxation (uniaxial\_tension). Each task provides a detailed natural-language specification; the agent writes the input script without executing LAMMPS.

We use a two-stage metric. Stage 1 (structural) is a deterministic regex-based check covering 11–15 per-task criteria: required commands, expected command patterns, task-specific physics markers, and coarse temperature/step-count range checks. It verifies that required commands and parameter fields are present and roughly plausible, but does not fully evaluate whether parameter values are correct relative to the ground-truth solution. Stage 2 (LLM judge) provides the task specification, a ground-truth script, and the agent-generated script to Claude Sonnet 4.6 and elicits an integer score from 0 to 10 along with a rationale. LLM judge scores are not fully deterministic at temperature 0 (runs through OpenRouter exhibit per-call variance); we report scores from a single evaluation pass and treat them as approximate rankings rather than precise measurements. Mean LLM judge score is the primary metric; structural score is a secondary reliability indicator.

**Factor-style readout.** Using the 6-cell subset per backbone and reporting single-run descriptive main effects:

*Claude:* R: +0.52, S: −0.30, X: −0.10, M: +0.09

*DeepSeek:* R: +1.55, S: +0.91, X: +0.83, M: +2.13

On DeepSeek, M exhibits the largest descriptive main effect: providing the primer contributes an average marginal gain of over two points relative to the unguided baseline. The best overall DeepSeek configuration is the full stack {M,R,S,X}, which suggests interaction effects among the factors also play a role. R (RAG) is second, suggesting that access to the LAMMPS example and documentation corpus matters substantially for this model. On Claude, the baseline is already strong and all effects are small; the only reliably positive factor is R.

**Structural scores.** The structural check is the LAMMPS equivalent of XML validation in GEOS, but it is less strict: it primarily verifies that required commands and parameter fields are present and roughly plausible, rather than fully evaluating whether the assigned values match the ground-truth solution. This is why both Claude and DeepSeek achieve near-identical structural scores across all configurations (≥ 0.976)—both models reliably include all required parameters regardless of which adapters are active. The LLM judge, by contrast, compares the actual values assigned to those parameters against the ground truth. This is where the two backbones diverge: both consistently produce scripts with the right parameters, but DeepSeek without guidance assigns wrong values to more of them. The near-ceiling structural scores confirm that failure in this domain is never a matter of agents omitting whole sections of the script; it is always about the correctness of specific values—physical constants, lattice densities, ensemble parameters, command argument ordering.

**Task- and solution-level analysis.** Beyond identifying which adapter modules help, we can ask what it is about specific tasks and their correct solutions that determines how much benefit the adapters provide. Looking at per-task gains when adding M and R to the DeepSeek baseline (Table H.1, {} → {M,R}): the five tasks with the lowest DeepSeek baseline scores (lj_melt=2, crack_2d=2, lj_indent=2, msd_diffusion=3, nvt_water=3) account for almost all of the mean gain. The two tasks with the highest baseline scores (lj_solid=8, lj_melt_minimal=9) are essentially unchanged or hurt by the adapters—DeepSeek lj_melt_minimal drops from 9 to 4 with {M,R}, recovering to 9 only in other configurations.

This pattern suggests that adapter gains are concentrated precisely where the baseline model lacks simulator-specific knowledge: tasks that already score highly leave little room for improvement, whereas tasks requiring specialized LAMMPS conventions benefit substantially from retrieval and domain-specific guidance. More concretely, the tasks with the largest gains are those whose correct solutions depend on knowledge that is not reliably reproduced from general training. For lj_melt (the biggest single gain, +7), the correct solution requires using the reduced LJ number density as the lattice argument and unfixing the NVE integrator before switching to NVT—both pitfalls the primer explicitly lists. For nvt_water (+5), the correct solution requires a complete TIP3P molecular topology with bond and angle coefficients, SHAKE constraints, and long-range electrostatics; the RAG library contains matching water examples that establish the exact command pattern. For lj_indent and msd_diffusion, the correct solutions rely on specific fix and compute syntax that deviates from what the model uses without reference.

In contrast, tasks where the correct solution follows a straightforward pattern that closely matches common MD examples—lj_solid, lj_melt_minimal—show no benefit, and adapters can introduce noise. crack_2d is the hardest case: it gains somewhat from adapters (DeepSeek {} → {M,R}: 2→5, Claude {} → {M,R}: 3→6) but still scores below average in every configuration. The correct solution requires placing a thin notch spanning the full x-length of the box but only a narrow y-range (−0.5 to 0.5), relative to a box that extends ±20 in y. Getting the notch coordinate logic right is a geometric reasoning problem, not a knowledge lookup, and neither the primer nor retrieval fully resolves it. crack_2d remains the hardest task across both backbones and all adapter combinations.

**Why the adapters help.** The failure mode analysis across all 12 agents points to two consistent classes of mistakes that the adapters correct. M (the primer) addresses knowledge errors: agents without it make LJ unit convention mistakes—for example, passing a lattice constant as a reduced density, or using real argon parameters in a LJ-unit script—and command ordering errors such as running create_box before defining a region, or leaving two integrators active simultaneously by failing to unfix NVE before adding NVT. These errors appear repeatedly across multiple agents and tasks. R (RAG retrieval) addresses syntax precision errors: agents without access to working reference scripts produce invalid lattice style names, incorrect fix command argument ordering, and undefined compute references. These are exact-token mistakes that a retrieved working example corrects immediately. The two adapters therefore target different error types: M supplies domain knowledge and conventions, R supplies exact syntax.

**Why the DeepSeek gain is larger.** The 3.2-point DeepSeek gain (4.56 → 7.78) versus the 0.56-point Claude gain (6.33 → 6.89) reflects a difference in baseline knowledge. Claude vanilla already assigns mostly correct values to the required parameters—its 6.33 LLM judge score shows that without any guidance it already handles most LAMMPS conventions correctly. The remaining Claude errors tend to occur on tasks requiring precise geometric reasoning (crack notch placement), which neither M nor R fully resolves. DeepSeek vanilla at 4.56 makes more of the knowledge-correctable errors—unit convention mistakes, command ordering violations, syntax failures—that M and R directly target. The adapters substantially narrow the baseline gap, allowing DeepSeek to match or exceed Claude performance on this benchmark. Claude's errors, already fewer and concentrated in harder geometry-dependent tasks, leave less room for the same adapters to improve.

**Structural complexity and which adapters matter.** The task's structural complexity also partly explains which adapter provides the most lift. Simpler tasks—lj_solid, lj_melt_minimal—closely match examples in the LAMMPS library and present few conventions to get wrong; both Claude and DeepSeek score near-ceiling on them even without guidance. More structurally complex tasks—couette_flow (SLLOD algorithm with deformational thermostat), nvt_water (charged molecular topology with SHAKE constraints), crack_2d (2D notch geometry)—require precise knowledge of conventions that the primer encodes directly. These also happen to be the tasks where DeepSeek's baseline scores are lowest, which is part of why M produces the largest gain for DeepSeek.

**Interpretation.** The LAMMPS result replicates the core finding—the plugin recipe transfers—but shifts the dominant mechanism. In GEOS and OpenFOAM, S (forced end-of-turn verification) was the largest reliability effect because it prevented agents from silently failing to produce required outputs. In the LAMMPS benchmark we observed little evidence of silent failure; instead, performance differences were driven primarily by the correctness of assigned parameter values. Here M (the primer encoding critical pitfalls) and R (access to reference examples) carry the quality signal. The strongest evidence for transfer is the DeepSeek result: a model that scores 4.56 without guidance reaches 7.78 with the full adapter, matching or exceeding the performance of guided Claude configurations through informational scaffolding alone. We do not claim the LAMMPS result has the same evidentiary weight as the GEOS benchmark—it is single-seed, scored by a non-deterministic LLM judge, and uses a different metric. What it does show is that the SIGA adapter recipe is not tied to XML, to a specific schema, or to catastrophic-failure prevention: in a domain where correctness is the bottleneck rather than completeness, the recipe adapts by shifting weight from workflow enforcement to knowledge injection.
